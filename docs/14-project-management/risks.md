### RISK-001 — Gemini API Rate Limit Hit During Live Demo

| Field | Value |
|---|---|
| **Risk ID** | RISK-001 |
| **Risk Description** | During the live demo, repeated queries or the demo seed ingestion saturate the Gemini API rate limit (embeddings or generation), causing HTTP 429 errors that are visible to judges. |
| **Category** | External Dependency / API |
| **Probability** | High |
| **Impact** | High |
| **Risk Level** | Critical |
| **Mitigation** | (1) Request a quota tier upgrade from Google AI Studio before the demo day. (2) Implement exponential backoff with jitter on all Gemini API calls. (3) Cache embeddings: never re-embed a chunk that already has a vector in the database. (4) Cache recent query embeddings in Redis with a 1-hour TTL to avoid re-embedding identical questions during demo rehearsal. (5) Stagger seed script ingestion with configurable delays between batches. |
| **Contingency Plan** | If the rate limit is hit during the demo: (a) Switch the embedding layer to a local HuggingFace model (`sentence-transformers/all-MiniLM-L6-v2`) that was pre-loaded in the Docker image during build. This requires embedding dimensions to be configured as a runtime variable and the pgvector column to accommodate both 384 and 768 dimensions. (b) Pre-generate all demo query embeddings and store them as fixture JSON files; serve them directly during the demo without an API call. (c) Acknowledge the fallback to judges and explain the architecture — the retrieval logic is unchanged. |
| **Owner** | Backend lead |

### RISK-002 — PDF Parsing Fails on Complex Manual Layout

| Field | Value |
|---|---|
| **Risk ID** | RISK-002 |
| **Risk Description** | Real machine manuals often use complex multi-column layouts, scanned images, decorative tables, or embedded vector graphics for diagrams. PyMuPDF's text extraction may produce garbled text, empty pages, or misaligned columns that break the chunking pipeline. |
| **Category** | Technical / Data Quality |
| **Probability** | Medium |
| **Impact** | Medium |
| **Risk Level** | Medium |
| **Mitigation** | (1) Test the PDF parser against the actual PDFs to be used in the demo during Phase 1 — do not rely on test PDFs generated by the team. (2) Implement a text quality check post-extraction: flag pages where the character-to-page-area ratio is suspiciously low (likely an image-only page). (3) Design the section chunker to handle inconsistent heading detection gracefully — fall back to fixed-size chunking for pages that do not match any heading pattern. (4) For the demo, use synthetically generated PDFs (via reportlab) that are guaranteed to parse cleanly if real PDFs prove problematic. |
| **Contingency Plan** | If a real PDF fails to parse acceptably: use the synthetic PDF seed script (Phase 6) as the primary demo data source. The synthetic PDFs are designed to exercise all retrieval features without depending on parsing quality. Document the limitation honestly — judges understand that production-grade PDF parsing is an engineering challenge separate from the RAG architecture being evaluated. |
| **Owner** | Backend lead |

### RISK-003 — Cross-Encoder Reranking Too Slow for < 5s Response Target

| Field | Value |
|---|---|
| **Risk ID** | RISK-003 |
| **Risk Description** | The cross-encoder reranking step (running `cross-encoder/ms-marco-MiniLM-L-6-v2` locally) adds inference latency for each candidate chunk pair. With `MAX_RETRIEVAL_CHUNKS = 20`, 20 forward passes may push total query latency above the 5-second target, particularly on CPU-only demo hardware. |
| **Category** | Technical / Performance |
| **Probability** | Medium |
| **Impact** | Medium |
| **Risk Level** | Medium |
| **Mitigation** | (1) Profile the reranker in isolation during Phase 2 on the target hardware. (2) If latency is borderline, reduce `RERANKER_TOP_K` from 10 to 5 — the reranker only needs to resolve the top few candidates. (3) Cache reranker scores for (query, chunk_id) pairs with a short TTL; identical follow-up questions reuse cached rankings. (4) Load the cross-encoder model into memory at startup, not per-request, to eliminate model loading overhead. (5) Consider switching to `cross-encoder/ms-marco-TinyBERT-L-2` which is ~4x faster at a small quality cost. |
| **Contingency Plan** | If reranking cannot meet the 5-second target on demo hardware: remove the cross-encoder and rely on RRF fusion scores alone for the final ranking. This is a quality degradation, not a correctness failure — the system still returns relevant chunks, just in a less optimal order. Document this as a "production enhancement" in the architecture notes. |
| **Owner** | Backend lead |

### RISK-004 — pgvector Index Build Too Slow for Large Manuals

| Field | Value |
|---|---|
| **Risk ID** | RISK-004 |
| **Risk Description** | Building an HNSW or IVFFlat index on a large chunk table (thousands of vectors) can take significant time if triggered synchronously during or after ingestion. This may cause the demo seed script to appear to hang, or cause the first query after ingestion to be slow due to sequential scan fallback. |
| **Category** | Technical / Infrastructure |
| **Probability** | Low |
| **Impact** | Medium |
| **Risk Level** | Low |
| **Mitigation** | (1) Build the pgvector index offline — run `CREATE INDEX CONCURRENTLY` as part of the seed script after all documents are ingested, not as part of each document's processing pipeline. (2) Use `CREATE INDEX IF NOT EXISTS` so re-runs do not error. (3) For the demo corpus (3 PDFs, likely < 500 chunks), sequential scan performance is acceptable — the index is a production optimization. Set `SET enable_seqscan = off` in the session if a performance demonstration is needed. (4) Pre-build the index in the Docker image for the demo (embed the seed data as a database snapshot). |
| **Contingency Plan** | If index build is problematic: use `ivfflat` with a small `lists` parameter rather than HNSW — IVFFlat index builds faster at a small recall cost. For a demo corpus, this is imperceptible. |
| **Owner** | Infrastructure lead |

### RISK-005 — Disambiguation Algorithm Produces Too Many False Positives

| Field | Value |
|---|---|
| **Risk ID** | RISK-005 |
| **Risk Description** | The disambiguation algorithm may trigger on queries that are actually clear — for example, "How do I reset the control panel?" being treated as ambiguous when the technician's session context already implies a machine. Or it triggers on every query because the threshold is set too conservatively, making the system feel broken. |
| **Category** | Technical / Product Quality |
| **Probability** | Medium |
| **Impact** | High |
| **Risk Level** | High |
| **Mitigation** | (1) The `DISAMBIGUATION_THRESHOLD` environment variable allows threshold tuning without code changes. Start at 0.3 and adjust based on testing. (2) Disambiguation should only trigger when there is no active session machine AND the BM25 retrieval returns significant hits across multiple machines. (3) If a query contains an explicit machine name or model number, skip disambiguation entirely (pattern match before the disambiguation algorithm runs). (4) Test the disambiguation algorithm against the golden dataset (Section 2.6 of the evaluation framework) early — at least one test run during Phase 4 development. (5) Define a maximum disambiguation depth: if a session has already disambiguated once, do not re-trigger for follow-up questions. |
| **Contingency Plan** | If disambiguation is consistently misfiring during the demo: raise the threshold to suppress false positives. The trade-off is under-triggering on genuinely ambiguous queries (which the system handles by falling back to the best-matching machine, still within machine scope). For the demo, a system that occasionally answers for a slightly wrong machine is worse than one that asks one clarifying question — but a system that asks a clarifying question on every single message is unusable. Prefer under-triggering over over-triggering. |
| **Owner** | Backend lead |

### RISK-006 — LLM Generates Invalid JSON Despite Schema Enforcement

| Field | Value |
|---|---|
| **Risk ID** | RISK-006 |
| **Risk Description** | Despite using Gemini's `response_mime_type: "application/json"` and a JSON schema, the LLM occasionally returns malformed JSON — truncated due to token limits, containing escaped characters that break parsing, or mixing JSON with prose preamble. |
| **Category** | Technical / AI Reliability |
| **Probability** | Low |
| **Impact** | Medium |
| **Risk Level** | Low |
| **Mitigation** | (1) Implement 2-retry logic on JSON parse failure with a simplified schema on the second attempt. (2) Set `max_output_tokens` explicitly to prevent truncation — do not rely on defaults. (3) Pre-process the LLM response string: strip leading/trailing whitespace and any ` ```json ``` ` code fences before parsing. (4) Validate the parsed JSON against the Pydantic model schema and catch `ValidationError` separately from `JSONDecodeError`. (5) Log the raw LLM response on parse failure for debugging. |
| **Contingency Plan** | If both retries produce invalid JSON: fall back to extracting the answer text from the raw response as plain text. Construct a `StructuredAnswer` with the plain text as `answer_text`, an empty `citations` array, and `confidence_score: 0.0`. This degrades citation quality but keeps the system responsive rather than returning a 500 error. Log the fallback event as a high-priority alert. |
| **Owner** | Backend lead |

### RISK-007 — Docker Compose Fails in Demo Environment

| Field | Value |
|---|---|
| **Risk ID** | RISK-007 |
| **Risk Description** | The demo environment (judge-provided laptop, hackathon venue hardware, or organiser-provided VM) may have incompatible Docker versions, port conflicts on 5432/6379/8000/3000, networking restrictions, or resource constraints that prevent `docker compose up` from succeeding. |
| **Category** | Infrastructure / Environment |
| **Probability** | Low |
| **Impact** | High |
| **Risk Level** | Medium |
| **Mitigation** | (1) Test `docker compose up` on a clean machine (not the development machine) at least 24 hours before the demo. (2) Pin all Docker image versions — do not rely on `:latest` tags that may pull different versions in a different environment. (3) Pre-pull all required images: `docker compose pull` and save them to tar files as a backup. (4) Parameterise all ports via environment variables so they can be changed without editing `docker-compose.yml`. (5) Include a `docker compose config` validation step in the README. |
| **Contingency Plan** | If Docker Compose fails entirely: run the system natively. (a) Start PostgreSQL locally (or use a cloud PostgreSQL instance). (b) Run `pip install -r requirements.txt && uvicorn app.main:app`. (c) Run `npm install && npm run dev`. (d) Provide a `scripts/run_native.sh` script that executes these steps. Pre-test this fallback — it must work without preparation on demo day. As a last resort, use a pre-recorded video demonstration of the system running, with live Q&A on the architecture. |
| **Owner** | Infrastructure lead |

### RISK-008 — Judges Ask About Edge Cases Not Covered by Demo Data

| Field | Value |
|---|---|
| **Risk ID** | RISK-008 |
| **Risk Description** | During Q&A, judges may ask the system about error codes, procedures, or machine variants that are not present in the 3 demo PDFs. The system will correctly refuse or return insufficient evidence, but judges may interpret this as the system being broken rather than working as designed. |
| **Category** | Product / Demo Strategy |
| **Probability** | Medium |
| **Impact** | Low |
| **Risk Level** | Low |
| **Mitigation** | (1) Index more than 3 machine manuals if time permits — 5 synthetic PDFs with diverse error codes and procedures reduce the chance of a gap. (2) Ensure the synthetic PDFs cover a broad range of error code numbers (E-001 through E-500) and procedure types (calibration, maintenance, emergency stop, firmware update). (3) Prepare a verbal response for this scenario: "The system is correctly refusing because it only knows what it has been trained on. This is the intended behaviour — it won't hallucinate an answer for a machine it has no documentation for." (4) In the demo introduction, proactively explain the refusal behaviour as a feature, so judges expect and appreciate it. |
| **Contingency Plan** | If a judge's question hits a gap and the refusal looks bad: use the moment to demonstrate disambiguation. Ask for a machine name, narrow the scope, and show the system finding something adjacent. The architecture talk is more important than the specific answer. |
| **Owner** | Product / demo lead |
